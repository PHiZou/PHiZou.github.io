Recompete Radar Schematics

Four views of the same system. Public procurement data is downloaded, loaded into Snowflake, modeled by dbt, scored, copied into a small Postgres database, and served by an API to the web app. Each view uses a different systems-engineering notation because each answers a different question about that path. The Petri net, lineage graph and score map are interactive.

What talks to what

Solid arrows carry data, labeled with the script that moves it. The dashed arrow is control: the scheduler that starts the work. The data plane is on top and the scheduler sits underneath.

Why two databases

Snowflake holds everything: about 484k raw award rows plus every dbt model. Neon's free tier is 0.5 GB, so it only gets the tables the API reads. The award table goes over once, and mart_awards is recreated in Neon as a view over it so the same rows aren't stored twice.

How the refresh is scheduled

One GitHub Actions workflow is configured to run every Monday at 08:00 UTC. It runs refresh.sh, then dbt build, then sync_marts_to_neon.py, in that order. This is the configured schedule. Nothing on this page reports whether recent runs succeeded.

How a refresh runs

This is the weekly refresh workflow (refresh-data.yml) modeled as a coloured Petri net. Circles are states, bars are steps, and dots are tokens. Each token carries a colour: an agency, a download outcome, or the dataset. An orange bar is enabled. Click it to fire, or press Run. Click any circle to see its tokens.

Firing log
  1. Ready. 20 agency tokens queued, 4 download slots free.
Place · agencies queued
  • The slots place is a resource. xargs -P 4 in refresh.sh lets at most four USASpending downloads generate at once. A slot token goes back only when a download lands or gives up.
  • “download lands” hides a retry loop. Each agency tries up to six fiscal-year windows (2024, 2023, 2025, 2022, 2021, 2026), pausing 60s between them. Any one success is the full all-time history, so only six failures in a row leave an agency with nothing. The slider shows how rare that is.
  • ×20 is a barrier. The load waits for every agency to finish, whatever the outcome. --replace is per-agency safe: a red token means that agency keeps last week's rows instead of being emptied. The delete and COPY run in one transaction.
  • The workflow is three steps in order. refresh.sh downloads and loads, dbt build rebuilds and tests the models, and sync_marts_to_neon.py copies the served tables. If a dbt test fails, the run stops before anything reaches Neon.

How a contract gets scored

USASpending never says which contract replaced which, so the project infers it. An ended award's follow-on is the award from the same office and PSC that starts within −180 to +365 days of the end date and is closest in size. Two logistic regressions are trained on ended awards (about 94k rows in int_score_backtest), then applied to live ones.

follow-on probability f →
retention probability r →
incumbent_strength = 100 · r
recompete_score = 100 · f · (1 − r)
r = P(incumbent wins the follow-on | there is one)
f = P(a follow-on happens at all)
Hover the map. The score is highest in the top-left corner, where a follow-on is likely and the incumbent is weak.

The score combines the two fitted model outputs to rank contracts for follow-up; it is not a calibrated probability that a new vendor wins. Timing is left out on purpose, so filter on months_to_pop_end separately. The follow-on links are inferred. A placebo window (follow-ons 3–5 years out) measures how much of the signal is matching noise.
